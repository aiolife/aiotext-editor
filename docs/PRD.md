## 一、项目定位

### 1.1 产品名称

**AioTextEditor**（中文名：爱欧文本编辑器）

### 1.2 一句话定义

面向中文古籍整理、佛经校勘、内容编辑人群的**跨平台深度文本编辑器**，在保留轻量、便携特性的同时，提供专业级的简繁转换、多编码互转、正则替换、文件比较与批量处理能力。

### 1.3 目标用户

| 用户类型 | 典型场景 |
|---------|---------|
| 古籍 / 佛经电子化整理者 | 扫描或 OCR 后的文本需要 GBK / BIG5 / UTF-8 互转、繁简统一 |
| 内容编辑 / 校对人员 | 重复行去除、自动排版、规范段落 |
| 网站内容运营 | 批量清理论坛干扰码、统一空白与标点 |
| 程序员 / 高级用户 | 自定义替换表 + 中文正则表达式 + 批量脚本化处理 |
| 一般中文写作者 | 需要一个轻量、绿色的纯文本编辑器，不依赖 Office |

### 1.4 与已有方案的差异

- **vs TextPro 6.5**：保留几乎全部专业功能；脱离 Windows 限制；用现代 UI；文件以 JSON/YAML 配置，不再依赖注册表；支持 macOS / Linux。
- **vs iml-editor-lite**：从纯 Markdown 编辑器扩展到专业中文字处理；保留 iml 的轻量 Tauri 2 壳层、单一 API 接口模式、CodeMirror 内核。
- **vs VS Code / Sublime**：专注中文纯文本处理场景，开箱即用，无需安装扩展即可完成繁简转换、文件比较、批量转码。
- **vs NotePad++**：原生 Unicode、加词组级简繁判断、自定义替换表 + 中文字符集正则。
- **vs OpenCC CLI**：OpenCC 是底层引擎；AioTextEditor 在其之上加编辑器、UI、批处理、可视化歧义提示；常用的 6 种转换直接就是"功能"菜单里的可选项（§3.5）。

### 1.5 繁简转换引擎：OpenCC（基于 BYVoid/OpenCC）

- **词库来源**：OpenCC 1.4.2 标准词库（STCharacters、STPhrases、TSCharacters、TSPhrases、HKVariants、JPVariants、TwVariants、TwPhrasesIT、TwPhrasesName、TwPhrasesOther 等）。
- **提供 6 种转换**：s2t、t2s、s2twp、tw2sp、s2hk、hk2s（§3.5）。OpenCC 上游还有更多方向（如 `s2tw` / `t2jp` / 小篆），但本产品**只提供这 6 种**——其余已从引擎侧删除（`Direction` 枚举里没有它们，id 也会被拒绝）；确有需要时走 `Custom` 自定义配置。
- **集成方式**：使用 `opencc-sys` crate 静态链接 OpenCC C++ 库；OpenCC 的全部 JSON 词典在编译期嵌入到二进制。
- **优势**（vs TextPro 自带的 s2t/t2s.dat 词表）：
  - OpenCC 提供"标准异体字"识别，繁体转换后可避免使用不规范异体字。
  - 支持台湾、香港等地方化繁体的双向转换。
  - 支持"歧义片段"诊断（CLI `--ambiguities`），可直观提示一对多的转换结果。
  - 词库维护由社区持续更新，比 TextPro 内置词库更现代。
- **不抛弃 TextPro 特性**（数据已全部转换为开放文本格式，见[数据字典](./06-data-dictionary.md)）：
  - **异体字组表 `fc1`/`fc2`**：用于文件比较"忽略异体字（完全等同 / 部分等同）"，非简繁转换数据。
  - **不转换括号对**（`[]` 等）作为前处理保留。
- **已废弃的 TextPro 数据**（均不再随包分发）：
  - 简↔繁单字表 `s2t.dat`/`t2s.dat`：与 OpenCC 词库完全同质，按 v0.3 决策由 OpenCC 取代。
  - BIG5 回退表 `u2b1.dat`/`u2b2.dat`：按 v0.5 决策弃用，改用 GitHub 上的 [`encoding_rs`](https://github.com/encoding-rs/encoding_rs)（WHATWG Encoding Standard 参考实现）承担全部编码互转——原生支持 **UTF-8、UTF-16、GBK、GB2312、GB18030、Big5、ISO-8859-1** 等编码；不可编码字符按标准以数字字符引用 `&#xNNNN;` 写出。
- **用户自定义替换表**通过 OpenCC 原生"内联字典（Inline Dictionary）"机制实现：程序把用户的 `A/B=目标` 自动转换为 OpenCC `{"type":"inline","entries":{...}}` JSON，作为转换链的最后一步叠加。
- **逆转换提醒**：对于"一对多"的转换字符，提供"OpenCC 歧义片段"诊断（CLI `--ambiguities` 风格）。

### 1.6 设计哲学（仿 iml 风格的四条规矩）

1. **没有欢迎页，启动即编辑** —— 上次未保存的内容自动恢复，但不强制建索引、不弹窗邀请。
2. **存不存由用户决定，自动保存默认关闭** —— 一切写盘操作需要用户明确触发。
3. **丢也是用户在决定** —— 任何关闭动作都必须给出「保存 / 不保存 / 取消」三条出路；选了「不保存」，改动当场丢弃，且**不会**在下次启动的会话恢复里复活。会话恢复只兜用户**没来得及做选择**的意外（崩溃 / 断电 / 被系统终止），不能覆盖用户已经明确做出的丢弃决定（判定规则见 §3.4）。
4. **不在背后做事** —— 没有云同步、没有 AI 写作、没有遥测，也**没有任何网络请求**：应用不检查更新、不自动更新版本，完全离线运行。

### 3.4 标签关闭与未保存处理（v0.3 增补，列入 v1.0 必交付）

> **为何单独成节**：`02-functional-spec F-01 §1.2` 对关闭只有一句话「关闭标签或退出应用时，若有未保存内容，弹框询问」，既没有定义选项，也没有定义批量行为与「不保存」的后果；`04-ui-ux §2.1` 的菜单表已列出「全部保存 / 关闭全部」；`05-roadmap` 第九阶段注记 ④ 遗留的会话边界问题同样归属此处。本节把这三处一并收口。

#### 用户故事

> 我改完内容点标签上的 ×，除了「保存」和「取消」，还要有「不保存」——这次改动我不要了，就得能真的丢掉，而不是下次打开又被会话恢复出来。
>
> 我一次开十几个文件做整理，希望能有一条命令把它们全部关掉（或只关掉除当前这一个以外的其他标签）；待处理的未保存文件一次性问完，而不是被连弹十几次。

#### 需求与验收标准

| 编号 | 场景 | 应有行为 | 验收标准 |
|------|------|---------|---------|
| C-1 | 关闭**单个**标签（× / 中键 / 双击 / 右键菜单 / `Ctrl·Cmd + W`） | 未修改 → 直接关闭，不弹框；已修改 → 三选对话框：**保存**（保存成功后关闭；保存失败或取消保存 → **不关闭**）、**不保存**（丢弃改动并关闭）、**取消**（留在原地） | 三条路径各自可执行；保存失败时标签必定仍在 |
| C-2 | 从未保存过的新文件（无路径）选「保存」 | 走「另存为」选路径；取消另存为 = 不关闭 | 与「保存」共用同一出口，不另起一条流程 |
| C-3 | 选「不保存」 | 改动当场丢弃，且**从会话中移除**，下次启动不再以「未保存内容」的形式复活（判定见下文） | 关闭后会话文件不再含该标签；下次启动该标签不出现 |
| C-4 | **关闭其他**标签 | 除当前标签外的所有标签按 C-1 的规则处理 | 存在多个未保存标签时只做一次汇总询问（见 C-6），不得逐个连弹 |
| C-5 | **全部关闭**标签 | 关闭全部标签（含当前），规则同 C-1 | 标签栏清空；会话同步清空，下次启动回到单个空白标签 |
| C-6 | 批量关闭时存在 **N 个（N ≥ 2）未保存**标签 | 一次汇总询问「有 N 个文件尚未保存」+ **全部保存** / **全部不保存** / **取消**，并给出逐个查看的入口 | 交互次数 ≤ 2，不得出现 N 次连续弹框 |
| C-7 | **全部保存**（独立动作，不关闭任何标签） | 逐个保存所有未保存标签（无路径者走另存为），保存后保持打开状态 | 与关闭完全解耦；键位 `Ctrl + Shift + A`（兑现 `04-ui-ux §2.1`） |
| C-8 | **退出应用 / 关闭窗口**（标题栏 ×、`Ctrl·Cmd + Q`、注销 / 关机）<br />**⏸ v1.1**：本条要改 Rust 侧的窗口关闭事件，且 macOS `Cmd + Q`、Linux 窗口管理器这两条路径在 Windows 上无法验证，故本轮不做 | 存在未保存标签时拦截一次，复用同一套决策（全部保存 / 全部不保存 / 取消）；用户确认后才允许窗口销毁 | 三个平台均生效；**当前「点窗口 × 直接静默丢弃」的行为届时必须消失** |
| C-9 | 对话框通用行为 | 自绘对话框（替换现行的 `window.confirm`）；`Esc` = 取消；默认焦点落在**取消**；按钮文案直接用「保存 / 不保存 / 取消」，不用让用户猜的「确定 / 取消」 | 手感与无障碍属性对齐既有的 `UnmappableDialog` / `ReloadDialog` |

#### 入口与键位

| 动作 | 入口 | 键位 |
|------|------|------|
| 关闭当前标签 | 标签 ×、中键点击、双击标签、标签右键菜单、文件菜单 | `Ctrl / Cmd + W`（macOS 需留意系统保留键位，沿用 `shortcuts.ts` 的 `RESERVED_KEYS` 约定） |
| 关闭其他标签 | 标签右键菜单、文件菜单 | — |
| 全部关闭 | 标签右键菜单、文件菜单 | `Ctrl + Shift + W`（兑现 `04-ui-ux §2.1`） |
| 全部保存 | 文件菜单 | `Ctrl + Shift + A`（同上） |
| 保存 / 另存为（单个，已有） | 已有入口 | `Ctrl / Cmd + S`、`Ctrl + Shift + S` |

#### 「不保存」与会话恢复的关系（本节决议，一并收口 roadmap 第九阶段注记 ④）

会话（`session.json`）的定位是**意外丢失的兜底**，只有崩溃、断电、被系统杀进程这类「用户没来得及做选择」的情形才配消费它：

| 情形 | 是否由会话恢复 |
|------|---------------|
| 用户明确选了「不保存」（C-3） | **否**：立即从会话移除，不复活 |
| 系统关机 / 崩溃 / 进程被杀，用户未做选择 | **是**：照旧恢复——这正是会话存在的理由 |
| 「全部关闭」（C-5） | 会话写成空标签列表，下次启动回到单个空白标签——维持现状行为，不再列为待定项 |

#### 不在范围

- 标签拖出为独立窗口（v1.2，见 `04-ui-ux §4.1`）；
- 关闭后再找回（回收站 / 二次确认机会）——由 C-1 的三选承担，不额外增加一层；
- 标签关闭后仍保留标签内部的撤销栈（v1.1 之后再评估）。

### 3.5 顶栏菜单栏（v0.4 增补 / v0.5 改版，列入 v1.0 必交付）

### 3.6 多语言界面（v0.11 增补，列入 v1.0+）

> **为何单独成节**：界面文案至今全部**硬编码简体中文**，散落在各前端组件里。此前没有 i18n 基础设施（无 i18next / react-intl、无 `locales/` 目录），设置项里也没有语言一项。本节把「支持哪几种语言、译文怎么来、在哪里切换、生效边界在哪」一次收口。
>
> **为什么不做英文**：评估后主动放弃。英文需人工翻译且多为专业术语（编码名、OpenCC 方向、正则、替换表），翻译质量与长度都不可控——英文译文普遍长于中文，会撑破现有按钮与菜单布局，回归成本高。只做简 / 繁两语时，繁體可由 OpenCC 自动生成，**翻译人工为零**。

#### 用户故事

> 我在台湾用，界面上「软件」「打印」「文件」这些词看着别扭，希望能切成繁體，但**我编辑的文本内容不能被改动**——那是用户的东西，不是界面的东西。
>
> 装完在设置里能改成繁體就行——**安装程序本身不用管语言**，保持现在这样即可。

#### 目标形态

| 项目 | 定案 |
|------|------|
| 支持语言 | **简体中文（默认）**、**繁體中文**；不做英文界面 |
| 译文来源 | 简体为**唯一文案源**；繁體 = 对简体文案跑 OpenCC `s2twp` + 小覆盖词典。**不维护翻译文件** |
| 切换位置 | 视图 → 选项… → **外观** → 多语言；默认简体中文。注：v0.5 起「设置」已并入「视图」（见 §3.5），故不设独立「设置」顶级菜单；「多语言」归入「外观」tab（与主题、字体同页），不新增 tab |
| 持久化 | 写入 `settings.json` 的 `language` 字段 |
| 生效方式 | 前端**即时生效**；Rust 侧生成的文本（错误提示、工具目录）**重启后生效** |
| 安装时 | **维持现状**：安装程序不做语言选择，`tauri.windows.conf.json` 不改动。语言只在应用内切换 |

#### 需求与验收标准

| 编号 | 场景 | 应有行为 | 验收标准 |
|------|------|---------|---------|
| L-1 | 文案集中 | 界面文案抽离到集中文案表，组件内不残留硬编码中文 | 组件内无硬编码界面中文；新增文案必须进表。**条目数不写死进文档**，开工前实测统计一次作为工作量依据 |
| L-2 | 切繁體 | 切到繁體后，菜单栏 / 对话框 / 状态栏 / 提示 / 帮助页全部为繁體 | **冒烟新增繁體模式用例**：切到繁體后断言菜单栏各顶级项文本等于预期繁體串（预期值取 `s2twp` 对该词条的实际输出，如「文件」→「檔案」），并断言界面上不再出现对应简体写法 |
| L-3 | **用户数据不得被翻译** | 文档内容、文件名、搜索词、文件路径、自定义替换表词条一律**保持原样** | **冒烟新增断言**（繁體模式下）：①打开简体文件名的文件（如「会议记录.txt」），断言标签页文本仍为「会议记录.txt」；②搜索框输入简体词，断言输入框 `value` 仍为简体；③编辑器正文输入的简体内容不被改写。这是本节**最关键的验收项** |
| L-4 | 即时生效 | 前端文案切换后立刻变，不需重启 | 设置里切换，界面当场刷新 |
| L-5 | 后端文本 | 错误提示、工具目录名称、托盘菜单在**重启后**变为所选语言 | 重启后触发一次后端错误，提示为繁體 |
| L-6 | 默认与持久化 | 首次启动为简体中文；改过之后重启仍是改过的语言 | 改设置 → 重启 → 仍是繁體 |
| L-7 | 安装器不动 | NSIS 安装向导保持现有形态，不做语言选择 | `src-tauri/tauri.windows.conf.json` **零改动**；`displayLanguageSelector` 仍为 `false`，`languages` 仍为 `["SimpChinese","English"]` |
| L-8 | 不回归 | 默认简体下既有功能与测试不受影响 | 前端单测与既有冒烟用例全通过（冒烟依赖界面中文，故默认语言锁定简体） |
| L-9 | 冒烟覆盖繁體 | 繁體模式进入回归网，不被后续改动悄悄破坏 | `npm run smoke` 中新增繁體模式用例（对应 L-2 / L-3 的断言）；该用例在简体模式下不生效 |

#### 落地口径

- **繁體靠 OpenCC 而非翻译文件**：启动时对文案表批量跑一次 `s2twp` 并缓存（毫秒级），不在每次渲染时转换。实测样本（摘）：`文件→檔案`、`软件→軟體`、`字体→字型`、`缩进→縮排`、`打印→列印`、`鼠标→滑鼠`、`半角→半形`、`导入→匯入`、`数据→資料`、`项目→專案`、`内存→記憶體`；句子级同样正确（`文件已保存到磁盘 → 檔案已儲存到磁碟`）。未出现「面 / 麵」一类一对多错转。

- **不用覆盖词典**：个别词不是台湾习惯写法（`批处理 → 批處理`、`退出 → 退出` 而非 `結束`），
  **一律接受 OpenCC 原样输出**。理由：开覆盖词典就得维护一份「哪些词要改」的清单，
  而这类词的边界是主观的——改了 `批處理` 要不要改 `面`？清单会越滚越大，收益却不对应
  （用户看得懂，只是略别扭）。保持「繁體 = s2twp 的确定性输出」这条简单规则，比逐个词
  打磨更可维护。日后若真有台湾用户反馈，再按反馈增量补也不迟。
- **不做 DOM 层统一转换**（曾评估过、已否决）：那样改动量明显更小，但必须维护一份「哪些区域不许转」的排除清单，漏一处就会误转用户数据（见 L-3），且每新增 UI 都要复查清单，属长期维护债。故采用集中文案表方案。
- **改动面**：前端各组件的界面文案；Rust 侧面向用户的文本（`error.rs` 的错误变体、`pipelines.rs catalog()` 的工具名等）；`language` 设置链路 4 处（`core/settings.rs`、`platform/tauriApi.ts`、`store/settingsStore.ts`、`SettingsDialog.tsx`）；**安装器零改动**。具体条目数开工前实测统计一次，**不写死进文档**（数字会随功能增删而变，写进规格就变成硬承诺）。

#### 不在范围

- 英文界面（评估后主动放弃，理由见本节开头）；
- **安装程序的任何多语言改动**：既不做安装时语言选择，也不把安装时选择传给应用（后者需另建 NSIS 模板写入注册表，收益不抵成本）；
- 用户自定义内容的任何语言转换——那是 F-03 转换功能的事，与界面语言无关；
- 日文 / 韩文等第三种语言（若日后加回英文，只需往文案表里填一套译文，框架不用动）。

### 3.7 启动性能与稳健性（v0.14 增补）

> **为何单独成节**：v0.13 做完多语言后，按 Beautiful Rust（Google Rust Style Guide、
> Rust API Guidelines、Effective Rust、Rust Design Patterns、Microsoft Pragmatic Rust
> 五个来源的综合）审了一遍 Rust 代码，发现两类问题：一是**启动路径上做了不该做的
> 重活**，二是**一批静默丢信息的 `as` 转换**。前者是用户每次启动都付的代价，后者
> 是潜在的正确性风险，都需要明确的验收口径，否则改完没法判断算不算达成。
>
> **版本说明**：本节交付的是 **v0.14.0**，不是 v1.0。§3.1 的 v1.0 十六项 MVP 与
> 第六节「验收标准（v1.0）」仍然存在、仍然有效，但其中的**测试覆盖率 ≥90%**与
> **冷启动 <1.0s** 两条当前拿不出可核查的证据（只有「Rust 223 项单测全通过」，
> 没有覆盖率数字；冷启动需要在有 GUI 的机器上实测），故**不在 v0.14 宣称达成**，
> 留待真到 v1.0 时统一验收。不要因为本节做了性能优化就顺手宣称 v1.0 达标。

#### 目标形态

| 项目 | 定案 |
|------|------|
| 繁體文案 | **按需加载**：仅当界面语言为繁體时才向后端取转换结果，简体（默认）下启动完全不碰 OpenCC |
| 设置读取 | 进程内缓存，启动路径上 `settings.json` **只读一次** |
| 前端包体 | 按 vendor 拆 chunk，让浏览器并行下载；首屏 JS 只装「能打字」必需的部分 |
| 整数转换 | 不保留任何**静默**丢信息的 `as`；要么换成安全写法，要么显式断言并写明为何不会截断 |
| 布尔结构 | 超过 3 个 `bool` 字段的结构收敛为语义明确的写法，避免调用点靠位置记参数 |

#### 需求与验收标准

| 编号 | 场景 | 应有行为 | 验收标准 |
|------|------|---------|---------|
| P-1 | 简体下不付繁體的代价 | 界面语言为简体时，启动**不触发** OpenCC 词典展开与加载 | 启动后 `%TEMP%` 下**不出现** `aiotext-opencc-*` 目录；首次切到繁體时才展开 |
| P-2 | 设置只读一次 | 启动路径上 `settings.json` 只做一次磁盘读，后续取用走内存 | 启动时序里 `settings::load()` 的磁盘读次数为 1（加日志或断言验证） |
| P-3 | 首屏 JS 可并行下载 | 主 chunk 不再把 CodeMirror、React 与业务代码打在一起 | 构建产物中 `vendor-react` / `vendor-codemirror` / `vendor-tauri` 与业务 `index` 分离。**注意：首屏 JS 总量基本不变**（编辑器是首屏必需），收益是并行下载与「改业务不必重下第三方库」的缓存命中，不是体积变小 |
| R-1 | 转换不静默丢信息 | 33 处 `as` 转换（`core/text_diff.rs` 20、`core/batch.rs` 4、其余分散）要么改写为 `try_from`/`saturating` 等安全形式，要么保留 `as` 但就地注明为何不会截断 | `cargo clippy -- -W clippy::pedantic` 中 `cast_possible_truncation` / `cast_sign_loss` / `cast_possible_wrap` 三项为零，或每处有 `#[expect]` + 理由 |
| R-2 | 布尔参数可读 | 9 处「bool 过多」的结构（`clippy::struct_excessive_bools`）按语义收敛 | 同上：lint 归零或有具名豁免；调用点不再出现连续两个字面 `true/false` 难以分辨的写法 |

#### 落地口径

- **繁體按需加载是修回退，不是新优化**：v0.13 把「启动时一次性取回全部繁體文案」
  写成了无条件执行，导致简体用户（默认路径）每次启动都白白付出 OpenCC 展开
  **28 个文件**（6 个配置 JSON + 22 个 `.ocd2` 词典）并加载词典的开销——而他们
  根本用不到繁體。这属于多语言功能引入的性能回退，必须修掉。
- **不改 `data_dir()` 的懒加载设计**：它本身已经是 `OnceLock`（`core/opencc.rs`），
  设计是对的，只是被上面的无条件调用提前触发了。修调用点，不动机制。
- **编辑器组件不拆**：`Editor.tsx` 是「能打字」的关键路径，拆成动态 import 只会
  把可交互的时间点往后推（v0.13 的注释已记录此决定）。要拆的是 `MenuBar`、
  `SearchPanel`、`ToolOptionsDialog` 这类非首屏必需的大组件。
- **`as` 转换逐处判断，不批量替换**：审计发现这些转换绝大多数是**理论风险**
  （Myers 差分算法的索引算术，实际不会越过 `isize::MAX`），把它们一律改成
  `try_into().unwrap()` 只会换来一堆新的 panic 点。故按 Beautiful Rust 的口径：
  能用安全写法就换，不能换就保留 `as` 并就地写明边界为何成立。
- **本节不引入 BeautifulRust 的 `lints.toml`**：接入会让现有约 300 条 pedantic
  警告（大量是缺 `# Errors` 文档）变成硬错误，需要单独一轮清理。留作后续，
  本节只解决其中的正确性相关项（R-1 / R-2）。

#### 不在范围

- v1.0 验收标准中的覆盖率与冷启动实测（留待 v1.0）；
- 把 pedantic 全量警告清零（大量是文档项，收益不抵改动面）；
- 转换、批处理等**运行期**性能的优化——本节只管**启动**；
- 前端框架替换或 CodeMirror 配置重构。

### 3.8 拖拽打开文件（v0.14.1 增补）

> **问题**：文件只能用「文件 → 打开…」吃到的对话框打开。用户从资源管理器 / 桌面把
> 文件拖进来——这是编辑器类软件的肌肉记忆——**没有任何反应**。本节补上这条路径。

#### 目标形态

拖拽打开文件，在**两个入口**上都可用，且表现与执行「文件 → 打开…」**完全一致**：

| 入口 | 场景 | 定案 |
|------|------|------|
| **拖到界面** | 应用已打开，把文件拖进窗口 | 全部打开为标签 |
| **拖到图标** | 应用未运行，把文件拖到桌面快捷方式 / exe 上 | 启动并把这些文件打开 |
| **拖到图标** | 应用**已在运行**，把文件拖到图标上 | 复用已有窗口，把这些文件打开（单实例转发） |

#### 需求与验收标准

（编号 `D` = Drag & Drop）

| 编号 | 场景 | 应有行为 | 验收标准 |
|------|------|---------|---------|
| D-1 | 拖一个文件到界面 | 走**同一条**打开链路（编码自动识别 → 新标签 → 进会话） | 拖入 xxx.txt，内容与用菜单打开该文件完全一致（含编码 / BOM / 换行识别结果） |
| D-2 | 一次拖多个文件 | **全部**打开为标签，与「打开」命令一致 | 拖 3 个文件 → 新增 3 个标签，顺序与拖入一致 |
| D-3 | 拖已打开的文件 | 复用现有标签并激活，不重复开第二个 | 已经打开 A.txt 再拖 A.txt → 标签数不变，且切到那个标签 |
| D-4 | 拖文件夹 | **无声忽略** | 拖入文件夹后标签数不变、不弹错（`tauri://drag-drop` 会把目录也送进来，按 Why-D-1 处理） |
| D-5 | 拖二进制文件（exe / png / zip） | 照常尝试读取，与菜单打开二进制的结果一致 | 不新增白名单、不弹「不支持」——见 Why-D-2 |
| D-6 | 拖到图标（应用未运行） | 启动后自动打开这些文件 | 拖 1 个文件到 exe → 应用起来并已打开它，无需再手动打开 |
| D-7 | 拖到图标（应用已运行） | 已有窗口**被带到前台**并在其中打开，不开第二个窗口 | 已有实例运行时拖文件 → 仍是单窗口，文件在新标签里 |
| D-8 | 路径含空格 | 正确打开 | Windows 给带空格的路径裹了引号，必须剥掉（见 Why-D-3） |
| D-9 | 拖多个文件到图标 | 全部打开 | 同 D-2 |
| D-10 | 编辑器内的**文本**拖选（Alt+拖矩形选区）不受影响 | 保持原样 | 这是 CodeMirror 的 `rectangularSelection`，与文件拖放是两套机制，不得互相干扰 |

#### 落地口径

- **Why-D-1（为什么文件夹是"无声忽略"而不是报错）**：`tauri://drag-drop` 会把拖进来的
  目录也放进 `paths`。报「不支持文件夹」属于新增一道判定规则，而拖目录进文本编辑器
  本来就是误操作——静默忽略与「什么都不做」的结果一致，且不给用户制造噪音。
- **Why-D-2（为什么二进制不拦）**：现有「文件 → 打开…」没有扩展名白名单，拖二进制后
  读出一屏乱码，和菜单打开二进制的表现**一样**。若只对拖拽加白名单，就会出现
  「菜单能开、拖拽不能开」的分裂，还得维护一份扩展名清单（并挡掉打开无扩展名文件
  这类合法用法）。保持两条路径同规则：都尝试读，都不预判。
- **Why-D-3（为什么要剥引号）**：Windows 拖文件到 exe 时，若路径含空格，Shell 传来的
  argv 里路径**带首尾双引号**（`argv[1] == "\"C:\\my dir\\a.txt\""`）。不去引号会去打开
  一个名为 `"C:\my` 的文件，必然失败且错误信息让人摸不着头脑。
- **不引入 `tauri-plugin-cli`**：拖到图标时 Windows 直接把路径作为进程参数给出，
  `std::env::args()` 足够；引入插件反而多一份依赖与配置。同时刻意**不做文件关联**
  （不写注册表），见「不在范围」。
- **界面拖放不需要 Rust 侧注册**：Tauri 2 在 Windows 上默认启用了拖放（`tao` 的
  `RegisterDragDrop` 接管了窗口），拖放**不会**被 WebView 当成 URL 导航（不会白屏），
  而是转成 `tauri://drag-drop` 事件交给前端。故前端直接 `listen` 即可。
- **启动参数不用「Rust emit → 前端 listen」取**：那会引入竞态——前端还没注册监听时
  Rust 就 emit 了，事件丢失。改为**前端主动拉**：启动时调一次 `take_startup_files`
  命令取出（并清空）缓存的路径。
- **单实例转发必须用 emit**：那是一条**跨进程**的路（第二个进程要把参数交给第一个），
  没有共享内存可用；此时第一个实例的前端必然已在监听，不存在上述竞态。

#### 不在范围

- **双击打开的文件关联**（不写注册表）：项目有「便携版不写注册表」的明确约定
  （`core/embedded.rs`），写 fileAssociations 与之冲突。拖拽是用户本次提出的场景，
  不做超出需求的扩展；
- 拖拽**文本内容**（把选中的字拖进编辑器）的位置控制——本次只处理文件拖放；
- 拖到图标时的数量上限：本次按 D-2 全部打开，不设阈值；
- macOS / Linux 的行为验证：本次仅在 Windows 上验证（拖到 .app 图标与 Windows 的
  进程参数传递机制不同），另两个平台**不宣称**已覆盖。

### 3.9 BeautifulRust 审核后的稳健性与热点优化（v0.14.2 增补）

按 **BeautifulRust 1.4.0**（`D:\site\aio1018\BeautifulRust-1.4.0`）的 `rust-review`
流程审了一遍 `src-tauri/`：先跑工具拿机械结果（`cargo fmt` / `cargo clippy` /
`cargo test` 全绿），再按「正确性 → 错误处理 → 惯用法」的优先级人工读代码。

先说三件定盘子的事：

1. **本轮审出一个真 bug**（Q-1），其余六项是把「能用但不对」的表达改成「错不了」。
2. **本项目是应用代码，不是库**（不对外发布 API），所以不套用 `#[non_exhaustive]`、
   避免过度泛型那类库规则；按 `rust-best-practices` §1 的「应用倾向简单直接」判断。
3. **本轮不给冷启动的量化收益**——见「落地口径」的 Why-Q-H1。

#### 目标形态

| 编号 | 类别 | 一句话 |
|------|------|--------|
| Q-1 | 正确性 | 单位加空格不再因大小写转换而错位 |
| Q-2 | 可达 panic | 批处理中一个文件 panic，不牵连其余成果 |
| Q-3 | 锁 | 读取设置不再持锁做磁盘 IO |
| Q-4 | 可达 panic | OpenCC 初始化竞态返回错误，不 panic |
| Q-5 | 热点 | 同一正则不重复编译 |
| Q-6 | 热点 | 替换表面板不再每次都扫一遍目录 |
| Q-7 | 错误处理 | 设置 / 会话读不出来时有据可查，不再静默走默认 |

#### 需求与验收标准

**正确性**

| 编号 | 场景 | 应有行为 | 验收标准 |
|------|------|---------|---------|
| Q-1 | 一行里出现「小写后会改变码点数」的字符（如 `İ` U+0130 → `i` + U+0307、`ﬁ` U+FB01 → `fi`），且其后还有「数字+单位」 | 单位识别与加空格的位置与**不含这类字符时一致** | 单测：`"İ5kg"`、`"ﬁ10px"`、`"正常5kg"` 三者的 `changed` 与输出均与逐字符小写化的结果一致 |

**可达 panic**

| 编号 | 场景 | 应有行为 | 验收标准 |
|------|------|---------|---------|
| Q-2 | 批处理过程中某个工作线程 panic（中毒锁） | 汇总阶段**照常返回已完成部分的统计**，不二次 panic | 单测：锁中毒时 `into_inner` 仍能取回数据；批次里坏文件不影响其余文件的统计 |
| Q-4 | OpenCC 数据目录并发初始化发生竞态 | 返回 `AppResult::Err`，不 panic | 代码路径上不再出现「丢弃 `set` 的 Result 后 `expect`」；失败时给出上下文 |

**锁与热点**

| 编号 | 场景 | 应有行为 | 验收标准 |
|------|------|---------|---------|
| Q-3 | 首个 `settings::load()` 触发读盘时，其他线程也调用 `load()` | 只有那一个线程等磁盘，其余**持有的是不带 IO 的短临界区** | `load()` 的缓存未命中分支里，磁盘 IO 不在任何 `MutexGuard` 的存活范围内 |
| Q-5 | 实时查找：用户在查找框里逐键输入 | 同一 pattern + flags 组合**只编译一次** | 单测：同 pattern 但不同 `opts`（如 `case_insensitive`）必须各得各的结果——缓存键漏掉 `opts` 就会「勾了忽略大小写却无效」，这是引入缓存最典型的错。**刻意不断言缓存条数**：那份缓存是全局共享的，`cargo test` 并行跑会让这类断言随机变红 |
| Q-6 | 打开替换表面板 / 列出替换表 | 内置表兜底（幂等展开）**每进程最多做一次** | 单测或日志：重复调用不再重复 `create_dir_all` + `metadata` 比对 |

**错误处理**

| 编号 | 场景 | 应有行为 | 验收标准 |
|------|------|---------|---------|
| Q-7 | 设置文件存在但读不出来（权限、损坏、只读介质） | 有一条 `tracing::warn`，带上路径与原因 | 定位失败时日志里能拿到失败原因，不再是纯静默 |

#### 落地口径

- **Why-Q-H1（为什么不写量化收益）**：`rust-best-practices` §12 要求
  「Design for usability first and optimize **after measuring**」。本会话起不来
  WebView2（上一版已验证：`npm run smoke` 的基线就是「等待调试端口超时」），
  拿不到冷启动耗时。**故 Q-3 / Q-5 / Q-6 只按代码推理陈述收益（减少了多少 IO、
  多少次重编译），不宣称「快了多少毫秒/百分之几」**。要真的度量，得在有 GUI 的机器上跑。
- **Why-Q-2（批处理的中毒锁为什么要恢复而不是随之 panic）**：
  `rust-best-practices` §5 说「Lock poisoning is fatal」，但那针对的是「继续用锁」；
  这里是 `into_inner()` **取出**内部数据且 Mutex 随即销毁，不是带病使用。
  批处理的价值恰恰在于「哪怕有坏文件，已完成的上千个成果也要交给用户」，
  所以此处不 recover 才是最坏的选择。代码里要把这个判断写明，免得日后被当反例外。
- **Why-Q-3（为什么读写分离的缓存不算过度设计）**：先把锁保护的范围缩到「存取一个
  `Option`」，脏活（读盘）放到锁外。与 Q-5 / Q-6 一样属于「用 once 标记代替重复劳动」，
  不引入新的抽象层，也不改变任何对外行为。
- **锁中毒的统一口径**：作为 Q-2 / Q-3 的副产品，其余 `lock().expect(...)` 一律保留
  「中毒即 panic」的语义（符合 Microsoft M-LOCK 的建议），**只在 Q-2 这一处**按上述
  理由 recover。不是把所有 expect 都改成 recover——那会把真 bug 藏起来。

#### 不在范围

- **不接入 BeautifulRust 的 `lints/lints.toml`**（沿用你 v0.14.0 的决定）：接入后
  `missing_docs` / `unwrap_used` 等会暴露约 306 条 pedantic 警告
  （其中 81 条缺 `# Errors`、42 条文档缺反引号、53 条缺 `#[must_use]`），
  多为文档项，收益不抵审查成本。项目 `cargo clippy` default 目前是 **0 warning**，
  已经很干净。
- **不清理 pedantic 的 306 条**：同上，留作后续单独一轮。
- **不改动任何对外行为**：本轮全部是内部实现调整——同样的输入必须给出同样的输出
  （Q-1 修正的是**原本就错**的输出，属于修复而非变更）。
-  **`core/opencc.rs` 里缺 `// SAFETY:` 注释的 5 个 `unsafe` 块**（§8 要求）：
  属文档补齐，本轮不动，记入待办。

### 3.10 冷启动实测与按热点优化（v0.14.3 增补）

上一版（§3.9）说「本轮不给冷启动的量化收益」，因为当时起不来 WebView2，拿不到数据。
这一轮**在本机真实测得冷启动耗时**，按数据定位热点再改，并把结果写回这里。

#### 测量方法

- 便携版 release 构建，每次跑之前清掉 `%TEMP%\aiotext-*`（OpenCC 数据 / 内嵌替换表
  都摊在那儿），模拟首次运行。
- 临时在关键节点插桩（量完即删），以 `take_startup_files` 被前端调用作为**「前端
  就绪」**信号——它是前端挂载后立刻发起的第一个 IPC，天然就是这个观测点。
- 5 次取中位数。

#### 优化前的实测分解（繁體界面、冷启动）

| 阶段 | 耗时 |
|------|------|
| `run()` → `setup enter` | 549 ms（Tauri 插件注册与窗口创建） |
| `setup enter` → **`tray build` 完成** | **470 ms** |
| 其中 `ui_lang::t` 首次调用 | 422 ms |
| 其中 `settings::load` 读盘 | **1 ms** |
| 其中 OpenCC 首次初始化（`data_dir` 38 ms + 词典 413 ms） | **451 ms** |
| `setup done` → 前端就绪（WebView + React 挂载） | 294 ms |
| **合计（到可用）** | **约 1258 ms** |

**结论**：启动慢不是因为读盘（`settings.json` 只要 1 ms），而是**托盘为两条菜单
文案触发了 OpenCC 首次初始化**——而托盘默认根本不显示。

#### 需求与验收标准

| 编号 | 场景 | 应有行为 | 验收标准 |
|------|------|---------|---------|
| Q-8 | 用户用 Windows 记事本「另存为 → UTF-8」改过 `settings.json`（文件带 BOM） | 设置**照常生效**，不静默回落默认 | 单测：带 BOM 的配置文件能解析出其中的非默认值；只有开头的 U+FEFF 被剥掉 |
| Q-9 | 默认（未开启「关闭时隐藏」）启动 | 启动路径上**不建托盘** | 冷启动到「前端就绪」由约 1258 ms 降至约 775 ms（实测中位数，-38%） |
| Q-10 | 开启「关闭时隐藏」后关闭窗口 | 托盘**照常出现**、进程不退出 | 实测：`CloseRequested` → `set_visible(true)` → 托盘建好（此时 OpenCC 已被前端预热，仅约 40 ms），进程存活 |

#### 落地口径

- **Why-Q-9（为什么是延迟建托盘，而不是让 OpenCC 变快）**：热点是「托盘为了两条
  菜单文案去初始化 OpenCC」，而托盘在默认路径下从不显示——**这笔工作本来就不该在
  启动时做**，延迟它比优化 OpenCC 本身更根本。且延迟后真正需要时只付约 40 ms
  （OpenCC 已被前端预热），用户无感。
- **Why-Q-8（顺带修的）**：测量过程中为了让「关闭时隐藏」生效去改 `settings.json`，
  用 PowerShell 的 `Set-Content -Encoding UTF8` 写出后**带了 BOM**，于是 `serde_json`
  整份拒收、设置静默回落默认——这才让关闭拦截没生效。**这不是测试脚本的小问题**：
  用户用记事本改设置会得到同样的 BOM，后果是所有设置归零且毫无提示。故一并修掉。
- **插桩已全部移除**：临时探针（写 `%TEMP%/aiotext-probe.txt`）只用于取数，
  量完已从 `lib.rs` / `tray.rs` / `settings.rs` / `opencc.rs` / `commands/*` 全部删除，

  自身的开销，本轮没有足够依据去动插件列表。

## 四、产品差异化亮点

1. **完全保留 TextPro 专业流程**：长期用户无需重新学习。
2. **跨平台原生体验**：使用系统 WebView，安装包控制在 12 MB 以内（参考 iml Lite 的 < 4 MB 目标，但要打包 OpenCC C++ 静态库约 +1 MB）。
3. **OpenCC 引擎 + TextPro 兼容**：业内最权威的中文简繁转换词库，覆盖台湾 / 香港地方化习惯；同时保留 TextPro 的异体字比较表（开放文本格式）。
4. **自定义替换表可叠加 OpenCC**：用户用熟悉的 `A/B=目标` 格式编表，无需学习 OpenCC 的 JSON 配置语法。
5. **内置中文增强正则**：GBK / BIG5 / 中文数字 / 天干地支等字符集，无需扩展。
6. **批处理可在 UI 上完全配置**：无需命令行。
7. **歧义片段可视化**：参考 OpenCC CLI 的 `--ambiguities`，转换后直接标注一对多区段。

## 五、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| OpenCC 三平台 cmake 构建 | 跨平台打包失败风险 | 第 1 周就在 CI 上 3 平台验证 `opencc-sys`；选用 docs.rs 收录的版本 |
| OpenCC C++ ABI 与系统库冲突 | 链接错误 | 使用 `link-cplusplus` crate，确保 CMake target `opencc` 独立 |
| OpenCC C API 仅接受磁盘路径 | 词典必须落盘 | 运行时把 JSON 配置写 `%TEMP%/aotext-cc-*.json`，OpenccHandle 持有句柄直到 Drop |
| 简繁转换一词多义问题 | 转换结果可能有少量错字 | 文档警示 + OpenCC 歧义片段诊断弹窗 + 用户词典可编辑 |
| BIG5 编码在 macOS / Linux 上没有内置字体 | 显示异常 | 打包字体内置或提示用户安装 |
| 非 Unicode 编码存在不可表示字符 | 直接保存 BIG5/GBK 会丢字 | `encoding_rs` 按 WHATWG 标准生成数字字符引用 `&#xNNNN;` + 保存前预检弹窗（改存 UTF-8 / 以引用继续 / 取消） |
| 自动编码识别误判 | 打开文件乱码 | 提供"重新载入"功能手选编码 |
| WebView 差异 | 部分平台功能不可用 | 走 iml 已验证的 macPDF / 平台适配方案 |
| 安装包体积超目标 | 用户体验下降 | CI 跑 `packaging.test.ts` 阈值测试 |
| 「不保存」与会话恢复语义相悖 | 用户以为丢掉了，下次启动内容又被会话恢复出来，等于「不保存」从未生效 | 按 §3.4 决议：显式丢弃即从 `session.json` 移除；用会话契约测试锁死「丢过的标签不复活」 |
| 退出窗口没有拦截机会（**已知遗留至 v1.1**，见 §3.4 C-8） | 点标题栏 × 会静默丢掉全部未保存内容，与 `F-01 §1.2` 承诺的「退出应用时弹框询问」相悖 | v1.1：Rust 侧接窗口关闭事件并阻止销毁，由前端复用同一套决策后再放行；macOS `Cmd + Q`、Linux 窗口管理器需在三平台验证清单里逐项确认。过渡期依托会话兜底（意外退出仍能恢复） |
| 批量关闭时弹框风暴 | 十几个未保存标签连弹十几次，用户会机械地一路点掉，反而更容易误丢内容 | §3.4 C-6 强制一次汇总询问，验收量化为「交互次数 ≤ 2」 |
| 顶栏命令堆积 | 每加一个功能就往顶栏塞一个按钮，窄窗口下按钮被截断、高频入口被挤走 | §3.5：顶栏只保留「文件 / 编辑 / 视图 / 帮助」四个文字入口，动作一律进菜单；快捷键始终是主路径 |

## 六、验收标准（v1.0）

- 安装包大小：Windows < 16 MB，macOS < 12 MB，Linux deb < 18 MB（包含 OpenCC 静态库后上调）。
- 启动时间：冷启动 < 1.0 s（8 GB 内存 SSD）。
- 打开 100 万字纯文本文件应不卡顿（按需启用 CodeMirror 虚拟滚动）。
- 全部 16 个 MVP 功能 ≥ 90% 测试覆盖率（Rust 端命令）。
- OpenCC 提供的 6 种转换方向均跑通且结果与 OpenCC CLI 一致；已删除的方向（s2tw / tw2s / t2tw / tw2t / t2hk / hk2t / t2jp / jp2t）在**引擎侧**就被拒绝，不是"UI 不显示但还能调用"。
- 未保存标签关闭时必须出现三选（保存 / 不保存 / 取消）；选「不保存」后内容**不再**写入会话、下次启动不复活（§3.4 C-1、C-3）。
- 关闭其他 / 全部关闭时，遇到多个未保存标签只允许一次汇总询问，交互次数 ≤ 2（§3.4 C-6）。
- ~~退出应用（窗口 ×、`Cmd + Q`、关机 / 注销）时拦截确认，三个平台均生效，不得静默丢弃~~ —— **顺延至 v1.1**（§3.4 C-8）：依赖 Rust 窗口关闭事件，需在三平台真机验证。
- 关闭与丢弃的相关路径有自动化测试覆盖：store 层批量关闭后 `activeTabId` 的收敛、UI 层三选决策与会话移除。
- 顶栏只有「文件 / 编辑 / 视图 / 帮助」四个纯文字入口：无品牌文字、无按钮边框、无 `▾` 角标；原来的平铺按钮动作全部可从菜单触达，启用条件逐项一致（§3.5 T-1、T-2、T-4）。
- 「文件 ▾」菜单的键位提示与用户当前快捷键绑定一致，改键位后即时反映（§3.5 T-3）。
